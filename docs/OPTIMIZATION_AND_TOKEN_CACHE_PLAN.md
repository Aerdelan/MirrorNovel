# MirrorNovel 生成链路优化方案与 Token 缓存方案

> 版本：v1（2026-08）
> 范围：`server/` 生成链路。本文档分两部分：A. 生成链路综合优化方案（生成流程 / 蓝图机制 / 长篇偏移）；B. Token 缓存与减耗方案（含已实施内容与后续路线）。

---

## A. 生成链路综合优化方案

### A0. 现状盘点（问题清单）

| # | 环节 | 问题 | 影响 |
|---|------|------|------|
| 1 | 每章正文请求 | 整份大纲逐字重发（`buildContextFromDocs` 直接注入 `outline`） | 5 万字大纲 ≈3.3 万 token/章；200 章 ≈660 万 token 纯重复 |
| 2 | 每章正文请求 | user prompt 内"稳定内容"（类型/主角/世界观/大纲/阶段记忆）与"逐章内容"（契约/字数）交错排列 | 前缀缓存命中率为 0，所有输入按全价计费 |
| 3 | 大纲生成 | ~~输出预算上限 12 万 token，prompt 只约束字数不约束结构~~ 已修复：输出封顶 1.6 万 token，字数下限全部删除，改为信息结构约束 + 反重复条款 | 大纲不再写满预算，中段换皮重复被封堵（见 A1.1） |
| 4 | 章节计划 | 输出预算 1.6 万~12 万 token 的巨型 JSON | 计划生成超时（45s/150s）率高，超时后 fallback 重建还要再花一次 |
| 5 | 用量可观测性 | 无任何 token 记账 | "消耗过大"无法归因到环节，无法验证任何优化收益 |
| 6 | 长篇偏移 | 无偏移度量，只在结局处被动补钩子 | 200+ 章后人物/时间线/伏笔漂移无法干预 |
| 7 | 专家模式 | 每章 2 次额外调用（reasoning 审稿 + polish 修订），无质量门控 | 好章节也要付全价审稿 |

### A1. 生成流程优化

**A1.1 输出预算结构化（已实施）**
`buildOutlineSpec` 已重构，核心思想：**长度是结构要求的涌现结果，不再是独立约束**。
- 删除全部字数下限（"全文不少于X字/主线不少于800字/阶段至少300字/结局不少于500字"）；
- 数量约束（阶段/节点/角色/支线数）保留——它们承担防塌缩功能，防止大纲过薄导致章节计划模型被迫自行发明结构；
- 新增信息结构约束：每个关键节点必须写清"触发条件→参与人物→具体事件→信息变化→后果与对下一节点的推动"；每个角色必须有一句"其他角色无法替代的功能"；
- 新增【反重复约束】：禁止"更强的敌人/更大的危机"式数字升级凑节点；相邻阶段必须改变人物关系或信息状态；"宁可短而具体，不要长而重复"（显式短许可，否则模型面对数量约束仍倾向用字数表现认真程度）；
- `outlineChars` 封顶 50000→20000，`outputTokens` 封顶 120000→16000（两者耦合，自动联动）。
收益：100 万字目标的大纲输出从最多 ~12 万 token 降到 ≤1.6 万 token；中段换皮重复被条款直接封堵，下游（章节计划/蓝图提案）拿到的素材信息密度更高。量级仍由 12 阶段 × 80 节点的结构要求保证（100 万字目标约 1.5-2 万字大纲），不会塌缩。

**A1.1b 章节计划输出预算（建议，未实施）**
章节计划输出预算改为"章数 × 220 token"封顶 24000：紧凑 JSON 格式每章实际约 150-220 token。

**A1.2 章节计划分级生成（建议，未实施）**
当前一次性生成整本书的章节计划导致超时与截断。改为两阶段：
1. 先生成"阶段级骨架"（约 12 个 phase，每个 60 token，总共 <1000 token 输出）；
2. 每写完一个 phase 前，再细化下一个 phase 的逐章计划（每次输出约 20 章 × 200 token）。
收益：单次调用永不超时；计划可以随剧情微调而不是开局锁死；每次只付小预算。

**A1.3 专家模式质量门控（建议，未实施）**
`runExpertReview` 先跑本地 `qualityScore`（chapterToolchain 已有，零 token）：分数 ≥ 阈值直接跳过 AI 审稿。预计专家模式减耗 40-60%。

### A2. 蓝图机制优化

**A2.1 蓝图渲染已经是"按进度筛选"的（现状良好）**
`renderStoryBlueprintForContext` 只输出当前章及之后的 ≤3 个 phase——这个设计本身就是 token 友好的，保持。

**A2.2 自动审核节奏（建议，未实施）**
当前每 6 章触发一次蓝图提案（reasoning 调用，maxTokens 2200）。建议改为"事件驱动 + 章节驱动"混合：
- 章节契约出现 `resolveHooks` 时（关键伏笔回收点）必审；
- 其余情况每 12 章审一次；
- 连续两次 `hasChanges=false` 后间隔翻倍（退避）。
蓝图提案 prompt 本身很短（9000 字上限），主要收益是减少无效调用次数。

**A2.3 蓝图提案的可执行性校验（建议，未实施）**
`normalizeProposedBlueprint` 目前只做结构归一化。建议增加：phase 覆盖连续性检查（上一个已确认 phase 的 endChapter 必须与新 phase 的 startChapter 衔接），避免用户应用一个有"章节空洞"的蓝图。

### A3. 长篇偏移优化

**A3.1 偏移度量化（建议，未实施）**
在 `updateCreativeState` 已经维护 characterStates/plotThreads 的基础上，新增每 10 章一次的本地（零 token）偏移评分：
- 人物位置连续性：上一章位置 vs 本章位置，无迁移理由则扣分；
- 时间线单调性：章内时间标记（"三天后"等）累计是否超过 phase 跨度；
- 伏笔老化：pending 状态超过 N 章（N = 计划回收章 - 设章）的伏笔数量。
评分写入 `novel.driftReport`，SSE 推送 `quality_notice`。先度量，再干预。

**A3.2 偏移纠正注入（建议，未实施）**
当偏移评分超阈值时，不额外调用 LLM，而是在下一章契约（`buildChapterContract`）里注入定向纠正指令（"本章必须包含：X 迁移到 Y 的过程"）。契约已经是每章必读的执行单元，借它纠偏成本为零。

**A3.3 contextMemory 检查点频率（现状良好，微调可选）**
当前每章更新 checkpoint（增量压缩，设计合理）。若后续发现 checkpointSummary 增长失控，可将 `compactLine` 的 10000 上限降到 6000。

## B. Token 缓存与减耗方案

### B0. 结论（先说答案）

**可以引入 token 缓存机制，且不需要改请求体、不需要额外接口。** 三层方案：

1. **服务商前缀缓存（被动，已实施）**：利用 DeepSeek/GLM/OpenAI 兼容线路自带的前缀缓存，通过把提示词重排为"稳定前缀 + 变化尾部"布局来命中。命中部分按约 1/10 价格计费。
2. **大纲分层渲染（已实施）**：从源头上砍掉每章重发的大纲中段，这是单项收益最大的改动。
3. **本地响应缓存（规划中，暂缓）**：对确定性调用（如重复的模板匹配）做本地缓存。调研结论：当前链路中不存在"相同输入重复调用"的热点（章节内容各不相同），收益不足以抵消失效复杂度，**不建议实施**，留作附录。

### B1. 已实施：三层改动详解

#### B1.1 大纲分层渲染 `renderOutlineForContext`（`services/novelContext.js`）

**原理**：大纲中段（当前进度附近的剧情）本就由"后续计划摘要 + 动态故事蓝图 + 章节剧情脉络"承载，逐字重发没有收益。分层只保留"开头（设定/人物）+ 结尾（终局落点）"。

**分层表（按写作进度分 5 桶，每 20% 一档）**：

| 进度 | 保留头部 | 保留尾部 | 说明 |
|------|---------|---------|------|
| 0-20% | 8000 字 | 2400 字 | 开篇阶段最需要完整设定 |
| 20-40% | 4200 字 | 2400 字 | |
| 40-60% | 3200 字 | 2400 字 | |
| 60-80% | 2400 字 | 2400 字 | |
| 80-100% | 1800 字 | 2800 字 | 临近结局，终局细节权重更高 |

- 短大纲（≤6000 字）原样通过，不做分层；
- 头尾裁剪在句子/换行边界进行（软裁剪），不产生半截句子；
- **关键设计**：同一进度桶内渲染结果逐字节一致——这是前缀缓存的命中前提。

**收益测算**（5 万字大纲、300 章目标）：
- 旧：300 章 × 50000 字 × 1.5 token/字 ≈ 2250 万输入 token；
- 新：300 章 × 平均 7000 字 × 1.5 ≈ 315 万输入 token，**降幅约 86%**。

#### B1.2 稳定前缀布局（`routes/novel.js`）

**原理**：服务商前缀缓存按"请求开头的连续相同字节"命中。旧布局中，逐章变化的契约/计划摘要夹在稳定内容中间，导致每章请求的前缀在变化点之后全部失效。

**新布局**（`buildStableChapterHead` + `buildChapterTail`）：

```
[system]  全书固定（generationContext + 题材契约）           ← 逐字节稳定
[user]    类型 / 主角 / 世界观                                  ← 逐字节稳定
          【已写内容与当前状态】分层大纲 + 阶段记忆 + 剧情线    ← 桶内稳定
[user]    【后续计划摘要】（当前章起 12 章）                    ← 每章变化
          章节契约 / 蓝图 / 字数状态                            ← 每章变化
```

同一桶（20% 进度）内约 20-60 章，每章请求的前 1 万-2 万字与上一章完全一致 → 深度前缀命中。

**兼容性**：`/generate` 整本与 `/continue/:novelId` 两个循环共用同一组构建器，行为一致；旧小说无任何迁移要求。

#### B1.3 Token 用量记账（`services/tokenUsage.js` + `Novel.tokenUsage` + SSE `token_usage`）

**原理**："消耗过大"必须先可度量。记账完全被动：

- `streamGenerate` 现在返回 `{ content, tokenCount, inputTokens, usage }`：
  - `usage`：服务商在流末尾返回的实际用量（DeepSeek 的 `prompt_cache_hit_tokens`、OpenAI 兼容线路的 `prompt_tokens_details.cached_tokens`、Ollama 的 `prompt_eval_count/eval_count`）——**不改请求体，被动解析**；
  - `inputTokens`：服务商未返回时的本地估算（`countTokens` 口径）。
- `recordTokenUsage(novel, role, stats)` 把每次调用记入 `Novel.tokenUsage`，按 outline/writing/reasoning/polish 四个角色聚合输入/输出/缓存命中量。
- 记账点覆盖：大纲生成、章节计划、每章正文、专家审稿（reasoning）、专家修订（polish）、蓝图提案（reasoning）。
- SSE 事件 `token_usage`（旧前端安全忽略，见 B3）实时披露累计值。

**记账示例**：
```json
{
  "inputTokens": 5200, "outputTokens": 950, "cacheSavedTokens": 3800, "calls": 1,
  "byRole": { "writing": { "inputTokens": 5200, "outputTokens": 950, "cacheSavedTokens": 3800, "calls": 1 } }
}
```
`cacheSavedTokens` 就是"前缀缓存命中量"——它乘以约 9/10 的价差就是本方案的直接账单收益，让缓存效果可以被验证而不是被相信。

### B2. 各线路缓存机制对照

| 线路 | 机制 | 是否需要请求体改动 | 本方案利用方式 |
|------|------|------------------|---------------|
| DeepSeek | 自动前缀缓存（≥64 token 前缀） | 否 | 稳定前缀布局直接命中 |
| GLM (OpenAI 兼容) | 自动上下文缓存 | 否 | 同上 |
| 通义/OpenAI 兼容 | `cached_tokens` 被动披露 | 否 | 记账读取 `prompt_tokens_details` |
| Ollama | 本地 KV cache（同会话同前缀） | 否 | 稳定前缀提升复用率 |
| Anthropic 风格 | `cache_control` 显式标记 | 是 | **未采用**：需要按 provider 分叉请求体，且当前线路表未配置该 provider；收益与 DeepSeek/GLM 自动缓存重叠 |

设计取舍：**只做零侵入的被动方案**。任何需要修改请求体或按 provider 分叉的方案，都被系统现存的"5 线路 × 4 角色"自由组合复杂度放大，维护成本高于收益。

### B3. 兼容性与安全

- **SSE 新事件 `token_usage`**：三个前端（client/admin/app）均采用 if/else 事件分发，未知类型被安全忽略，已核实无需发版。
- **Novel.tokenUsage**：Mixed 字段 + 按需创建，旧数据无迁移；`recordTokenUsage` 对损坏结构（数组/null）自愈重建。
- **大纲分层**：章节摘要/伏笔/记忆的"事实来源"地位不变，分层只影响大纲文本本身的注入量。上下文总上限 `maxChars: 14000` 截断逻辑保持。
- **回滚**：三处改动相互独立，任意单独 revert 不影响其他部分。

### B4. 预期收益汇总

以"5 万字大纲、300 章、专家模式关闭"为例：

| 措施 | 输入 token 变化 | 说明 |
|------|----------------|------|
| 大纲分层 | ~2250 万 → ~315 万 | 单项最大头 |
| 前缀缓存 | 命中部分 ≈1/10 计价 | 保守估计桶内稳定前缀 1.5 万字 × 20 token/字 × 260 章 ≈ 390 万 token 进缓存 → 账单层面相当于再省 ~350 万 token 等价 |
| 记账 | 0（纯观测） | 使上述数字可被验证 |

**综合预期：输入 token 总量下降 80%+，账单口径下降 85%+。** 实际数字以 `Novel.tokenUsage` 的实测为准——这正是记账存在的意义。

### B5. 后续路线（未实施，按优先级）

1. **A1.3 专家模式本地质量门控**——专家模式用户立即减耗 40-60%；
2. **A1.2 章节计划分级生成**——解决超时 + 减少计划 token；
3. **A1.1b 章节计划输出预算封顶**——与分级生成配合实施；
4. **A3.1 偏移度量**——先有数字再谈纠偏；
5. **admin 端用量面板**——把 `tokenUsage` 聚合到用户/线路维度。

（原第 1 项"输出预算结构化"已实施，见 A1.1。）

### 附录：本地响应缓存调研结论（不实施）

调研了"对确定性 LLM 调用做本地响应缓存"：候选点是 `matchTemplates`（已本地化，无 LLM）与章节关键词提取。结论是当前链路不存在"相同输入重复调用"的热点——每次章节调用都包含唯一上下文。缓存失效管理（蓝图更新、契约变化都会使 key 失效）的复杂度远超收益。若未来加入"多用户共享同一部合作小说"之类的场景，可重新评估。
