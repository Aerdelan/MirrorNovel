# 两层语义记忆（2026-10-27）

本次修改位于 `D:/MirrorNovel-main (2)`。它在上一轮长篇分批规划修复之上，将正式生成链路中的记忆升级为“单章语义总结 + 累计阶段记忆”。旧的本地提取器保留给旧数据读取、同步编辑和兼容路径使用；正常写作前会补齐有效语义记忆，不把简单截取当作模型总结。

## 第一层：逐章语义总结

- 数据保存在 `chapters[].memorySummary`，包含版本、章节号、正文 SHA-256、总结、已发生事件、已证实事实、人物状态、未决问题与回收证据。
- 只发送实际保存的正文与已经出现的未决问题，不发送后续章节计划来当作事实来源。每条事件、事实、人物状态和问题必须提供该段正文中存在的原文证据。
- 普通章节完整阅读。超长章节按最多 14000 字符切分，分段覆盖全文，避免只看开头和结尾；若分段总结超出单章记忆预算，再调用模型对各段语义总结合并，不能直接从中间截断。事实和事件的完整结构化记录继续保留。
- 总结与正文哈希、章节号一致时复用缓存。正文修订、删除或章节重排后，失效记录在下次写作前补齐。
- JSON、条目数量、证据归属和回收问题 ID 都有校验；格式失败再请求一次，仍失败则保留旧版本。原文证据校验不是对语义推断正确性的完整证明，模型仍可能误读人物猜测，需要真实作品验收。

## 第二层：累计阶段记忆

- 默认每六章，用“上一版累计记忆 + 新增单章总结”生成新的 `contextMemory` v2。
- 保存累计剧情、完整事实账本、仍开放的问题账本、人物最新状态和正文来源哈希。原始逐章记录继续保留，模型选择重点索引不会删除完整账本。
- 未决问题只有在逐章总结给出已知问题 ID 和本章原文回收证据后才被移出开放账本；后续没提及不会自动视为解决。
- 输入模型的索引有数量上限，避免每次合并重发越来越大的全书正文或完整账本；生成时按当前剧情选择相关事实，字面相同的记录不会重复占满提示词。
- 正文修订后，旧累计记忆标记失效并排除出生成上下文，保留旧快照直到成功重建。未改动章节的单章总结复用缓存，受影响的累计阶段重新合并。

## 生成与恢复

整本生成、整本续写、单章续写、导入续写和指定章节追加均接入已保存章节的语义记忆。导入的原始参考文本仍由原有导入提示词承载，本模块总结的是实际已保存章节。

新正文先按原有提交校验保存、确认提交，再更新语义记忆。因此模型总结失败不会擦除正文，也不会要求重复生成已提交章节。整本循环记忆失败时暂停，继续操作先补齐记忆，再决定是否生成下一章；单次导入/追加已经提交成功时仍报告正文成功，并明确提示记忆待更新，下次写作前严格补齐。

用户手动编辑、恢复版本及删除章节不会立即发起模型收费调用；记忆先失效，后续写作前再更新。元数据写入单章 `memorySummary` 路径，避免仅更新记忆时主动标记整个正文数组替换。

运行过程沿用所选推理线路，发送 SSE 状态与心跳，暂停信号传递给模型请求。成功、校验失败返回以及带服务商用量的请求错误，都纳入既有推理用量账本；新章总结和当次阶段合并计入该章的用量快照，旧书补齐等恢复调用纳入整本账本。

## 开销与发布

普通新增章节通常增加一次总结调用，每六章再增加一次阶段合并。超长章节、结构校验重试和记忆修订重建会增加调用。旧作品第一次续写需要逐章补历史，可能明显增加等待和 Token；每章独立保存，暂停或中断后复用已成功的缓存。没有在读取书架或详情时自动运行全书收费总结。

本次新增章节可选字段，其他记忆字段仍使用已有 Mixed 字段，不需要批量数据库迁移。不修改现有小说正文、模型默认配置或前端业务流程；更新服务端代码并重启后续写时生效。桌面打包模式需要将相应服务端源码一并打包。
